### Что именно изменилось в упакованных манифестах

Сравнены **полные** манифесты собранных APK (`apkanalyzer manifest print`, символические имена ресурсов восстановлены через `aapt2 dump resources`). Двоичные манифесты **не идентичны** исходным. После учёта следующих различий остальное структурно совпало в каждом варианте:

- **Разрешения:** единственная дельта — объявление `<permission>` уровня `signature` (`0x2`) и `<uses-permission>` **того же** app-owned разрешения: `com.vivotomirpay.stub.debug.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` в debug и `com.vivotomirpay.stub.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` в release. Это защита неэкспортируемых динамических приёмников AndroidX Core на API 25–32, не новый системный доступ и не запрос разрешения пользователю. Остались без изменений `QUERY_ALL_PACKAGES`, `VIBRATE`, `FLASHLIGHT`, `ACCESS_NETWORK_STATE` и `moe.shizuku.manager.permission.API_V23`.
- **Прежние компоненты:** те же пять метаданных Vivo у приложения и `SwipeEntryActivity`, тот же `vivo.intent.action.NFC_BUS_SWINGSPLASH` с `DEFAULT`, имя, экспорт, label, `singleTask`, `taskAffinity`, `noHistory`, `excludeFromRecents`, `configChanges` и прозрачная тема. Не изменились `MainActivity`, неэкспортируемая `MenuActivity` со своим task и темой, `allowBackup=false`, все package/intent `queries` и `rikka.shizuku.ShizukuProvider` (существующий экспорт, `${applicationId}.shizuku`, `INTERACT_ACROSS_USERS_FULL`, `multiprocess=false`). Скомпилированные `TransparentSwipeTheme` и `MenuTheme` совпали; `AppTheme` добавляет `adjustResize` для IME в обеих темах.
- **Редактор:** прежняя неэкспортируемая `MenuEditorActivity` удалена, редактор теперь маршрут Compose; отдельная оконная `MenuActivity` осталась.
- **Оба варианта:** AndroidX добавляет `androidx.core.app.CoreComponentFactory` и неэкспортируемый `androidx.startup.InitializationProvider` с `${applicationId}.androidx-startup` и инициализаторами EmojiCompat, Lifecycle и ProfileInstaller. Это внутрипроцессная инициализация, не новая доступная извне точка входа.
- **Оба варианта:** `androidx.profileinstaller.ProfileInstallReceiver` включён, `exported=true`, `directBootAware=false`, защищён требованием к **отправителю** `android.permission.DUMP`. Четыре действия: `INSTALL_PROFILE`, `SKIP_FILE`, `SAVE_PROFILE`, `BENCHMARK_OPERATION` с префиксом `androidx.profileinstaller.action.`. Это новая привилегированная служебная поверхность, не запрос `DUMP` приложением и не доступ обычных приложений к действиям продукта.
- **Только debug:** `androidx.activity.ComponentActivity` из `ui-test-manifest` сохранена для Compose-тестов, но итоговый манифест делает её `exported=false`. На прежнем APK явный запуск через `adb shell am start` проходил, на итоговом тот же вызов из UID оболочки отклонён (`SecurityException: not exported`); instrumentation по-прежнему запускает тестовый хост. По сравнению со сборкой до исправлений это единственное смысловое изменение debug-манифеста; release-манифест после сопоставления имён ресурсов совпадает, а манифест тестового APK совпадает побайтно.

Дополнительных привилегий продукта или изменений доступности его прежних компонентов в release не обнаружено. Это оценка упакованных метаданных, а не доказательство отсутствия любых рисков зависимостей.

### Границы переноса точки входа (Task 9)

На закреплённом Kotlin 2.1.21 применены **локальные** `INVISIBLE_REFERENCE`/`INVISIBLE_MEMBER` для прежних прямых вызовов Kotlin file-private/JVM package-private `HiddenApiCompat` и `ARGUMENT_TYPE_MISMATCH` для сохранения nullable Java-вызова `getLaunchIntentForPackage`. Компилятор предупреждает, что поведение подавленных ошибок не гарантировано при обновлении. При смене Kotlin повторить сборку обоих вариантов, проверку JVM ABI и байткода (два прежних `invokestatic` для CTS, nullable fallback без новой проверки). Java ABI-клиент Task 9 компилировался, но не выполнялся. `450L` для камеры проверено по байткоду; тест на эмуляторе подтверждает несинхронное закрытие, а не фактическое время, внешнее приложение камеры или реальный CTS.
