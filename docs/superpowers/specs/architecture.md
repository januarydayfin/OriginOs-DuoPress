# Архитектура: миграция Double Power Key

## 1. Контекст и ограничения

В `:app` на Java главный экран совмещает представление, настройки, системные запросы и выбор действия; остальные UI — редактор, пикер ярлыков и панель запуска. Требуется перенести приложение на Kotlin + Compose с MVI и реализовать [дизайн C](2026-11-25-kotlin-compose-mvi-design.md), не меняя пользовательских и системных контрактов.

Ограничения:

- `applicationId`, существующий debug-суффикс, подпись, `minSdk 25`, `targetSdk 35` — `app/build.gradle`. Подбираем совместимые версии Kotlin и AndroidX без принудительного подъёма `minSdk`; изменения инструментария ограничиваем необходимым.
- Полное имя `com.vivotomirpay.stub.SwipeEntryActivity`, фильтр и метаданные Vivo, прозрачная тема, параметры task/history и поведение на блокировке сохраняются — `app/src/main/AndroidManifest.xml`, `SwipeEntryActivity.onCreate/onNewIntent`. Миграция launcher UI не меняет назначение Vivo-компонента.
- Формат файла `vivo_swipe_stub_prefs`, существующие ключи, `special:*`, `app:*`, `shortcut:…`, порядок JSON-массива, пустое меню и значения по умолчанию сохраняются — `PrefsHelper`, `ShortcutAction`. Ключи `double_press_package` и `torch_on` не сбрасываются; лимиты журнала остаются.
- Для запуска действий не требуется инициализация Compose или ожидание UI-состояния. `SwipeEntryActivity.handleSwipeIntent` и `MenuActivity.makeMenuItemRow` имеют общий `ActionRunner.runAction`; камера сохраняет особенности показа над блокировкой и существующую отложенную финализацию входной Activity.
- Для ярлыков сохраняются ограничения Shizuku Android 11+/ADB shell, существующие настройки provider/queries и разрешения — манифест, `ShizukuShortcuts.checkStatus`. Другие действия от Shizuku не зависят.
- Не допускается удвоение владельцев настроек в период миграции — оба языка читают и пишут существующее хранилище, новый формат или синхронизация между двумя хранилищами не вводятся.

## 2. Точки решения

| Область | Выбор есть? | Варианты или правило |
|---|---|---|
| Размещение кода | Да | Пакеты в `:app` или выделенный JVM-модуль `:core`. Сейчас `settings.gradle` содержит только `:app`. |
| Контракты и реализация | Да | Локальные интерфейсы или межмодульная граница для чистых моделей и правил. |
| Владение данными | Нет | Один источник долговременного состояния — существующий файл настроек. Текущее системное состояние читается из Android, а не сохраняется как настройка. |
| Управление состоянием | Частично | MVI обязателен. Выбор дизайна: небольшие контракты `UiState` + `UiIntent` для экранов и сценариев, не один общий store. |
| Интеграция | Да | Ручная сборка зависимостей в `:app`; либо `:app` собирает реализации Android и контракты `:core`. Навигация настроек — Navigation Compose, системные входы — отдельные Activity. |
| Слой данных | Нет | Совместимый `SharedPreferences`, каталог приложений и статусы Android/Shizuku; сеть и БД не нужны. |
| Feature toggle | Нет | Это замена интерфейса, а не сосуществование двух интерфейсов в релизе. Промежуточные шаги проверяются отдельно вне релиза. |

## 3. Варианты

### Вариант A. Один модуль, раздельные пакеты

Компоненты UI, состояния, хранения и Android-интеграции остаются в `:app`. UI сначала вызывает существующую логику через временные адаптеры, затем адаптеры переключаются на эквивалентные Kotlin-реализации; публичный системный вход не перемещается.

### Вариант B. Android-приложение и JVM-модуль

В `:core` выделяются типизированные значения настроек, правила меню, кодек action ID и контракты хранилища. В `:app` остаются экраны/MVI, реализации для Android и системные точки входа. Миграцию можно разделить на те же шаги, но появится дополнительная граница API и сборки.

## 4. Оценка

| Критерий | A | B |
|---|---|---|
| Соответствие правилам зависимостей | Сохраняется существующий `:app`; границы поддерживаются пакетами. | `:app` зависит от нового `:core`; `:core` не зависит от Android или `:app`. |
| Разделение ответственности | ViewModel владеет UI-состоянием, один адаптер владеет доступом к файлу настроек. | Те же владельцы состояния; чистые правила дополнительно отделены границей модуля. |
| Расширяемость: новый VPN-клиент; новые правила порядка меню | Клиент добавляется в платформенный пакет `:app`; правила порядка — в код меню того же модуля. | Клиент добавляется в `:app`, правила порядка — в `:core`, изменения контрактов затрагивают оба. |
| Тестируемость | Правила, кодеки и ViewModel с фейками тестируются JVM-тестами `:app`. | Правила и кодеки тестируются без Android Gradle Plugin; MVI и Android-интеграция остаются в `:app`. |
| Объём и стоимость | Заменяются 15 production Java-файлов (часть без аналога), переносится прежний тест; ориентир 25–40 новых Kotlin-файлов вместе с тестами, один модуль. | Те же функциональные изменения плюс новый Gradle-модуль, настройки зависимостей и несколько межмодульных контрактов; ориентир 30–45 новых Kotlin-файлов вместе с тестами. |
| Риск по impact | Максимум CRITICAL: `ShortcutAction` (3 прямых, 8 затронутых по отчёту), `getMenuItems` (3/11), `saveTriggerLog` (7/7), `FlowLayout` (4/5). `runAction`: HIGH, прямые `handleSwipeIntent`, `makeMenuItemRow`, 3 затронутых по отчёту. | Те же риски и те же системные вызывающие. Перенос кодеков через межмодульную границу добавляет изменения зависимостей, но не снижает риск прошивок. |

**Рекомендация**: A — один модуль даёт нужную тестируемость без второго контура сборки, а поэтапность позволяет проверить новый UI отдельно от переноса системных вызовов. Границы можно усилить позднее, если появится повторное использование правил вне приложения.

GitNexus upstream также отметил HIGH для `PrefsHelper.getTargetPackage` (4 прямых, в том числе `handleSwipeIntent`), `MainActivity.startShortcutFlow` (1 прямой, `showActionPicker`), `VpnController.controlVpn` (`runSpecial`) и `HiddenApiCompat.showSessionFromSession` (`triggerCircleToSearch`). Прямые вызывающие `getMenuItems`: `resolveMenuItems`, `rebuildList`, `mutate`. `saveTriggerLog` вызывают `runAction`, `saveShortcutResult`, `runSpecial`, `toggleFlashlight`, `launchCamera`, `triggerCircleToSearch`, `launchApp`. `FlowLayout` используется в `lockChips`, `chipsRow`, `patternChips`, `vpnClientChips`. Это показатели графа, а не проверка работы на устройстве: связи через манифест и платформу контролируются отдельно. План должен уточнить impact по каждому изменяемому символу перед правкой.

## 5. Детализация

### Вариант A

Компоненты:

| Компонент | Ответственность | Модуль | Статус |
|---|---|---|---|
| `MainActivity` / `AppNavHost` | Хост Compose и три корневых маршрута; Activity исполняет системные UI-запросы. | `:app` | [`MainActivity.java`](../../../app/src/main/java/com/vivotomirpay/stub/MainActivity.java) → Kotlin, `AppNavHost` новый. |
| Экранные ViewModel и контракты MVI | Преобразуют пользовательские намерения и данные в состояние действий, настроек, диагностики, редактора и пикеров. | `:app` | Новые; заменяют императивное состояние UI и callbacks. |
| Репозиторий настроек | Читает/пишет совместимые значения и наблюдает реальные изменения. | `:app` | Новый контракт на базе [`PrefsHelper.java`](../../../app/src/main/java/com/vivotomirpay/stub/PrefsHelper.java); реализация затем Kotlin. |
| Android-адаптеры | Package Manager, статус обработчика/ассистента/VPN, Shizuku, запуск действий. | `:app` | Новые границы для существующих [`ActionRunner.java`](../../../app/src/main/java/com/vivotomirpay/stub/ActionRunner.java), [`VpnController.java`](../../../app/src/main/java/com/vivotomirpay/stub/VpnController.java), [`ShizukuShortcuts.java`](../../../app/src/main/java/com/vivotomirpay/stub/ShizukuShortcuts.java) и платформенных запросов `MainActivity`. |
| `SwipeEntryActivity` | Обработка системного Intent Vivo и выбор целевого действия по состоянию блокировки. | `:app` | [`SwipeEntryActivity.java`](../../../app/src/main/java/com/vivotomirpay/stub/SwipeEntryActivity.java) → Kotlin. |
| `MenuActivity` | Хост панели действий над экраном блокировки; выполняет выбранное действие через общий исполнитель. | `:app` | [`MenuActivity.java`](../../../app/src/main/java/com/vivotomirpay/stub/MenuActivity.java) → Kotlin + Compose. |

Интерфейсы:

- Экран → ViewModel: `onIntent(UiIntent)`; ViewModel → экран: неизменяемый `StateFlow<UiState>`, lifecycle-aware подписка. Сетевых или системных вызовов на этапе композиции нет.
- ViewModel → репозиторий: наблюдение снимка, изменение отдельных настроек и атомарное по отношению к другим операциям редактора изменение меню. Репозиторий → точка входа: совместимый синхронный снимок для холодного запуска без ожидания потока.
- Хост → Android: явные внешние команды (системный выбор обработчика/ассистента, настройки приложения или разрешение Shizuku), результат возвращается в сценарий. Контекст Activity не хранится во ViewModel. Очередь UI-запросов с ID в состоянии и подтверждением исполняющего хоста не переотправляет уже запущенную команду после рекомпозиции или поворота; внешний запрос не возобновляется автоматически после смерти процесса.
- Системная Activity или меню → общий исполнитель: запуск сохранённого действия с имеющимися Intent/контекстом и результатом для журнала. Навигация внутри приложения принадлежит `NavHost`; экранные ViewModel не хранят `NavController`.

Направление зависимостей:

- Compose → экранный контракт/ViewModel → интерфейсы настроек и системного состояния; Android-адаптеры реализуют интерфейсы. Ручная сборка зависимостей в `:app`, без DI-фреймворка.
- `SwipeEntryActivity` / `MenuActivity` → совместимое чтение настроек и исполнитель; нет зависимости от настроечного `NavHost` или ViewModel главного экрана.

Поток данных:

1. При открытии экрана репозиторий отдаёт снимок настроек, Android-адаптер возвращает актуальные статусы. ViewModel сводит данные и локальные намерения в `UiState`.
2. Выбор из UI идёт через `UiIntent`; хранилище обновляется, а его наблюдаемое состояние обновляет все заинтересованные экраны. Временное положение ползунка не пишет на диск на каждый кадр; подтверждённое значение и тестовый виброотклик выполняются по завершении жеста.
3. Поиск и загрузка списка приложений/ярлыков выполняются вне главного потока с отменой по жизненному циклу экрана. Устаревший результат не подменяет новый поиск или состояние закрытого пикера.
4. Двойное нажатие отдельно читает текущую конфигурацию, выбирает действие, выполняет его и обновляет журнал. Диагностика наблюдает журнал; при `onResume` обновляются внешние статусы, в том числе после системного окна. Статус обработчика различает разрешение Intent в своё приложение, в другое приложение и отсутствие конкретного обработчика (например, системный resolver). В первом случае не проверяем, было ли явное назначение «Всегда»; при другом обработчике CTA использует существующее открытие сведений о пакете вместо отправки Intent, который запустил бы это приложение.

Обработка ошибок:

- Недоступный клиент VPN, пакет, ярлык или сервис Shizuku не сбрасывает сохранённый выбор. При подборе показывается пустое состояние или понятная ошибка; при запуске сохраняется диагностический результат в пределах существующих лимитов.
- Ошибка разбора меню получает существующий список по умолчанию; сохранённое `[]` означает пустое меню без подстановки. Ошибка применить изменение в UI не выдаётся за успешную замену.
- Повторные клики по разрешению и поздние callbacks не создают второй запрос; одновременные изменения списка применяются по очереди к актуальному состоянию.

Чего не делать:

- Не дублировать состояние настроек в нескольких ViewModel, не блокировать холодный вход на сборе `Flow` и не менять системный контракт вместе с редизайном — ограничения раздела 1, `README.md` («Как это работает», «Безопасность»).
- Не копировать самописные View-токены в Compose; использовать Material 3 в границах выбранного дизайна. Не заменять совместимое хранилище на DataStore в этой задаче.

### Вариант B

Компоненты:

| Компонент | Ответственность | Модуль | Статус |
|---|---|---|---|
| `ActionId` и правила меню | Кодирование/декодирование и ограничения списка без Android. | `:core` | Новый модуль; перенос правил `ShortcutAction` и `MenuEditorActivity`. |
| Контракт настроек и снимок | Формат значений для потребителей, без зависимости от `SharedPreferences`. | `:core` | Новый. |
| ViewModel и Android-адаптеры | MVI-контракты, доступ к хранилищу и Android, навигация и исполнение действия. | `:app` | Те же роли, что в A, общие модели импортируются из `:core`. |

Интерфейсы и зависимости: `:app` → `:core` через кодек, правила меню и снимок настроек; реализация хранилища и композиция зависимостей остаются в `:app`. Обратных зависимостей нет.

Поток данных: тот же, что в A. Android-адаптер преобразует сохранённое представление в модели `:core`, ViewModel отображает состояние, Android-хост выполняет системные команды.

Обработка ошибок: правила формата и списка возвращают результаты без Android-типов; `:app` преобразует их в сообщения либо пишет результат в журнал. Ошибки разрешения и жизненного цикла обрабатываются по тем же правилам, что в A.

Чего не делать: не передавать `Activity`, `Intent`, `Drawable` или `SharedPreferences` в `:core`; не выносить туда платформенную логику, которая по контрактам раздела 1 зависит от Android.
